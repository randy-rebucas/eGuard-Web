# Release, 2026-11-16: removed devices, Apple revocation, child-device PIN, Android audit fixes

Commit `04fefe9`. This file is for whoever deploys the web app and for the teams building the clients: Android, iOS,
Windows agent and browser extension.

The release has four parts:

1. **Removed devices can still be released.** A computer removed without its own confirmation, or any removed phone
   or tablet, keeps its token on the server for 30 days. During that time `/sync`'s `401` carries eGuard's signed
   uninstall command.
2. **Sign in with Apple revocation** (App Store guideline 5.1.1(v)). Deleting an account or unlinking Apple revokes
   eGuard at Apple.
3. **Child-device parent PIN and iPhone app rules.** A family PIN opens "Parent settings" on a child's iPhone, where a
   parent blocks apps or gives them a daily time. The phone reports what it chose as counts.
4. **Server fixes from the Android audit.**
   - An app's own limit gets its own alert.
   - Parent-API `429`s carry `Retry-After`.
   - The device API's `401` carries a code.
   - Android alert pushes are data-only.

The full API reference is in [mobile-api.md](mobile-api.md), [child-app-spec.md](child-app-spec.md),
[desktop-agent-spec.md](desktop-agent-spec.md) and [browser-extension-api.md](browser-extension-api.md), all
updated in the same commit.

## 1. Deploy

Ship the code and the migrations together. Without the migrations, the code fails on `RemovedComputer`,
`Family.devicePinHash` and `Device.appRules`.

1. Back up the production database.
2. Deploy. `prisma migrate deploy` applies these in order:

   | Migration | Change |
   |---|---|
   | `20261116180000_removed_computers` | New table `RemovedComputer` (unique `deviceId` and `tokenHash`, indexed by family, cascades with the family) |
   | `20261116200000_apple_refresh_token` | `OAuthIdentity.appleRefreshToken` (nullable text) |
   | `20261116210000_removed_phones` | `RemovedComputer.removalSecret` becomes nullable (phones and tablets have none) |
   | `20261116220000_device_pin_app_rules` | `Family.devicePinHash`, `Family.devicePinSetAt`, `Device.appRules` (JSONB) |

   All four are additive. No existing row is rewritten.
3. Set the Apple keys in the production environment. Each is described in `.env.example`.

   | Variable | Value |
   |---|---|
   | `APPLE_TEAM_ID` | The Apple developer team id |
   | `APPLE_KEY_ID` | Id of a key with "Sign in with Apple" enabled for the app's primary App ID |
   | `APPLE_PRIVATE_KEY` | That key's `.p8` file as PEM (`\n` for newlines is fine) |
   | `TWO_FACTOR_KEY` | Already required in production. It now also seals the stored Apple refresh tokens |

   Without the Apple variables, Apple sign-in still works, but no token is stored and nothing is revoked. Apple
   sign-ins made before these are set have nothing to revoke later.
4. Nothing to schedule. The existing maintenance job gains a step, "expired removed computers", which deletes
   `RemovedComputer` rows past `expiresAt`.
5. Check after deploy:
   ```sql
   SELECT count(*) FROM "RemovedComputer";             -- 0 right after deploy, grows as devices are removed
   SELECT count(*) FROM "Family" WHERE "devicePinHash" IS NOT NULL;
   ```

## 2. What parents see on the website

- **Devices page, "Removed computers".** This lists computers removed before they confirmed it. For each it shows
  the name, when it was removed, its live removal code, until when the code works, and until when the row is shown
  (30 days). Copy in alerts and confirmations now says the computer removes eGuard by itself the next time it's
  online.
- **Settings › Family › "Child device PIN".** The family admin can set, change or remove a 4–8 digit PIN. Every
  change goes into the audit log (`device_pin.set` / `device_pin.cleared`).
- **Device page, iPhones: "App rules on this iPhone".** This shows what was chosen on the phone, for example
  "Blocked: 3 apps, 1 category · 1 h 30 min a day: 2 apps", or "None yet."
- **iPhone screen-time limits** now show what they count: "2h / day · counts 1 app". The child picks those apps on
  the phone, so a limit that counts only one app is easy to spot.
- **Data export** leaves out the PIN hash, as it does for passwords.

## 3. API changes

### Parent API (`/api/mobile/v1`)

| Endpoint or area | Change | Client action |
|---|---|---|
| `GET /family/device-pin` | **New.** `{ set, setAt }`; never returns the PIN | Show whether a PIN is set |
| `PUT /family/device-pin` | **New.** `{ pin }` (4–8 digits) or `{ pin: null }` to clear. Admin only. Stored argon2id | Settings › Family row. Send an explicit `null` to clear |
| Device objects | New `appRules` and `appRulesLabel` (iPhones only, otherwise `null`) | Show `appRulesLabel` on iPhone devices |
| `POST /auth/social` | Optional `authorizationCode` (Apple only) | iOS: send it on every Apple sign-in, and again on the `guardian: true` retry |
| `DELETE /me`, `DELETE /me/identities/{id}` | Also revoke Apple at Apple (best-effort; never fails the request) | None |
| `DELETE /devices/{id}` | A computer removed without waiting, or after 7 quiet days, gets a 30-day `RemovedComputer` | Show `pending` and the removal code; offer Keep / Remove now (Android added this today) |
| Any `429` | Now carries `Retry-After` (seconds) | Show when to try again |
| Alert pushes (FCM) | Android tokens get **data-only** messages: `title`/`body` in `data`, high priority, no `notification` part. iOS is unchanged | Android: post the notification from `onMessageReceived` (already done) |

### Device API (`/api/device/v1`)

| Endpoint or area | Change | Client action |
|---|---|---|
| `401` body | `{ error, code: "device_unknown" }`. For 30 days after a removal it also carries `uninstall: { command, signature, keyId }` | Unpair only on `device_unknown`. A bare `401` comes from something in between (a proxy, a captive portal), so keep enforcing and retry |
| `POST /parent-unlock` | **New.** `{ pin }` → `200 { ok }`, `403` wrong, `409` no PIN set, `429` + `Retry-After` after 5 tries in 15 minutes per device. Each unlock and wrong try is audited | iPhone Parent settings; Android child mode's Settings lock |
| `POST /sync` request | iPhones may send `appRules` (counts) | iOS only |
| `POST /sync` response | New `parentPinSet` (boolean) | Lock settings only when it's `true` |
| `POST /report` `SCREEN_TIME` | Optional `counts: { apps, categories, sites }`. Shown to parents, not compared with the policy | iOS only |
| `LIMIT_REACHED` event | Optional `app` (1–80 chars): that app's own daily limit. Gives its own alert ("YouTube time used up"), deduplicated per app per 12 hours. With `category`: a category limit. With neither: the day's limit | Send `app` for a per-app limit, never as the daily limit |
| `/events` allowance (120 an hour) | A repeated `eventId` and a `413` no longer count. An event answered `429` wasn't handled, so its retry counts | None |
| `UNINSTALL_ACK` | Accepted once from a removed computer's token (`200`), after which the row is gone | Windows agent |

### Browser extension API

| Area | Change | Client action |
|---|---|---|
| Policy | Every policy carries a signed `issuedAt` | Take the clock offset from `issuedAt` instead of the `Date` header. Never let time fall below the newest accepted value. Refuse an older copy (blocks a replayed or forged older answer) |

## 4. How the main changes behave

**Removed devices** (`lib/removed-computers.ts`).
- When a device's row is deleted without the device's own word, its token hash is kept in `RemovedComputer` for 30
  days (`REMOVED_COMPUTER_DAYS`). For a computer, its removal secret is kept too. That covers three cases:
  - a computer removed with "Remove without waiting";
  - a computer removed automatically after 7 quiet days;
  - a phone or tablet removed by a parent, or deleted along with its child.
- While the row exists, `/sync` answers that token with a `401` carrying the same signed uninstall command a sync
  answer would. The Windows agent then removes itself. The iPhone app lifts protection only with that command (or
  after 7 days of `401`s), so a proxy can't fake a removal.
- The row is deleted on `UNINSTALL_ACK` or when it expires. A child's deletion keeps a row for each of its devices,
  best-effort.

**Sign in with Apple** (`lib/apple-tokens.ts`).
- On sign-in, the server exchanges the app's one-time `authorizationCode` at Apple for a refresh token. It stores the
  token sealed with `TWO_FACTOR_KEY` on the `OAuthIdentity`.
- It revokes the token at Apple when:
  - the account is deleted (including every parent when an admin deletes the family);
  - Apple is unlinked;
  - the email changes;
  - a parent is removed from the family.
- Every step is best-effort. An expired code, a refusal or Apple being down is logged, and never fails a sign-in or a
  deletion.

**Child-device PIN and iPhone app rules** (`lib/device-pin.ts`, `lib/device-app-rules.ts`).
- The PIN is family-wide and hashed like a password. It's checked online only: the phone never holds the PIN or its
  hash.
- Apple doesn't give eGuard app names on an iPhone, so per-app rules there are chosen on the phone. A parent can block
  apps, and give up to 5 groups of apps a daily time. The phone reports them as counts.
- The server's name-based `apps` rules and `categoryLimits` still apply to Android and computers only.

**Android alert pushes** (`lib/push.ts`).
- `sendPush` takes the token's platform. Android tokens get data-only messages, so the app always builds the
  notification itself. That keeps its checks in force: only a signed-in parent sees alerts, and the lock screen shows
  a private version.
- Android app versions already installed read `title`/`body` from `data`, so they keep working.
- Parent-care pushes pass no platform and are unchanged.

## 5. Apps already installed

Nothing in this release breaks an app version that's already out:

- New response fields (`appRules`, `appRulesLabel`, `parentPinSet`, `issuedAt`, `code`, `uninstall`) are additive.
  Every client ignores unknown fields.
- New request fields are optional. Older apps that don't send `authorizationCode`, `app` or `counts` behave as
  before. They just get none of the new behaviour: no Apple revocation, and app limits are still alerted as the day's
  limit.
- Android 1.0.12 and earlier unpair on any device-API `401`, as before. The next Android build unpairs only after a
  second `401` at least 10 minutes after the first.
- Extension 0.1.4 accepts `issuedAt`, but stores the policy again on every sync until it's updated.
